# Shared gathering builder

All existing and newly created gatherings use the same builder for the common editing path. This does not certify every specialized page or integration against the permanent rules; known exceptions are listed in [the architecture audit](documentation-architecture-audit.md). The shared DOM retains some historical `wedding` IDs for compatibility with saved selectors; these IDs do not select a separate editor.

- `app.js:gatheringBuilderContext` creates the ID-bound context consumed by `SiteEditing`, `ElementEditor`, `ElementAppearance`, and `GapLayout`. Content and appearance use the same formatter and persistence path.
- `inline-editing.js` registers editable fields, text, pages, tabs, undo/redo, and text placement. `element-editor.js` supplies the single selection-based rich-text/formatting sidebar and autosave.
- `element-appearance.js` owns formatting groups and per-text-box styling. Title and introduction groups are separate. Groups share styling only inside the selected gathering. `fitted-text.js` fits titles from their saved font size rather than replacing it with a theme default.
- `GatheringFeatures` enables optional pages and RSVP capabilities. Wedding meal choices, wedding-party responsibilities, attire, shared wedding details, and timelines extend the content; they use the same builder and rendering/editing components.

`toolbar-layout.js` measures visible fixed toolbars (including safe-area padding) and supplies shared bottom clearance. `fitted-text.js` caches fitting inputs and preserves scroll position during temporary measurements. `GapLayout` resolves saved anchors against their current parent without rewriting saved placements; gallery completion refreshes spacing.

Text shadow/outline settings use the existing appearance groups for shared components and safe `TextStyles` markup for independent rich-text content. The serializer validates colors and bounded numeric effects; no arbitrary CSS is accepted. Effect spans are protected from legacy palette rewriting while editing and rendering. When older explicit effect declarations contain palette variables, serialization resolves only those explicit declarations to their displayed values; inherited effects are not captured. Applying an effect clears only matching effect declarations in the selected descendants, retaining unrelated rich formatting. Editable roots remain serialization boundaries rather than receiving unsaved inline styles. Formatting controls inspect the selected text run, falling back to the first text run instead of an unstyled wrapper. Button label highlight paints the label rather than the button surface. Explicit selected/unselected appearance groups take precedence over legacy element settings. Existing saved settings remain intact.

Formatting observation ignores editor controls, active editable text and transient gap markers. Genuine page/state mutations are coalesced into one animation-frame paint, while explicit rendering and appearance updates remain synchronous. The observer is disconnected during its own paint to prevent feedback from label wrapping/saved-markup restoration. Group classification is reused only for that paint and discarded afterward, preserving gathering/scope changes. The RSVP deadline timer updates notice text/visibility only when they change.

## Data and session boundaries

Gathering data stays in `appState.events[gatheringId]`. Existing keys remain intact: `siteText`, `textAppearance`, `elementAppearance`, `sitePages`, `siteTabTitles`, `siteTabOrder`, `siteElementOrder`, `siteElementPlacements`, `siteGaps`, and `siteSpacing`. RSVP header slots, dates, addresses, menus, RSVPs and wedding-specific settings also remain in that event object. The shared-context refactor did not require conversion into a new schema. Normalization still contains legacy migrations, including a Christmas menu-replacement exception documented in the audit. Existing legacy-selector migrations continue to preserve moved content.

The chooser uses `appState.gatheringHome`, independent of every gathering. Accounts and other explicitly site-wide services remain outside the builder's per-gathering content. Dropbox infrastructure is shared. Published folder links are event-specific, but the current R2 gallery is account-wide across gatherings; see the audit rather than assuming it has event isolation.

`finishGatheringBuilderSession` flushes pending text and controls, releases the selection, cancels its autosave timer, and restores temporary styles before changing the active gathering or replacing shared state. Field callbacks capture their event state. A context saves by its original gathering ID and cannot overwrite a replacement application state after a reload. Address edits update the selected gathering's own header and invitation fields, even if another gathering has the same address text.

Empty text slots have a small host-only editing outline so they can be selected and double-clicked. Guest rendering and saved text remain empty.

## Verification

Run `npm test` for state ownership, field bindings, formatting, feature permissions and RSVP behavior. With a local HTTP server on `127.0.0.1:8041`, run `scripts/verify-shared-gathering-builder.cjs` through Playwright. It blocks external traffic, creates a gathering through the real UI, edits titles/introductions and formatting in four gatherings, switches before autosave completes, compares untouched event objects, reloads local storage, and verifies desktop/mobile editing. It also preserves the wedding meal configuration. The other browser scripts cover layout, count menus, toolbars and wedding-specific flows. The Validate shared gathering builder GitHub Actions workflow runs the unit regressions and production build on pull requests and main pushes.

## Authorized persistence boundary (A1/A2 implementation)

The builder itself remains shared. `state-client.js` and `shared-state-protocol.js` now sit behind its save/load context: they keep an acknowledged baseline/revision, send conditional changes, and never advance a draft’s revision from an unadopted background read. The Worker authenticates hosts, returns scoped guest views and enforces RSVP/dish permissions server-side. Name-only guest identification and existing QR identifiers are retained, with their impersonation limitation stated explicitly. Conflicts preserve private drafts rather than force-replacing state. See [deployment approval, private backup and recovery requirements](state-security-rollout.md); activation is not performed by the implementation task.

## A5: recycled heading nodes with independent content

Wedding Party uses the same registered textarea/rich-text field pipeline as other page copy. `WeddingParty.headingFields` assigns per-page/member content keys to its shared DOM heading nodes. `ElementAppearance.textSelector` uses those keys only for text; `selector` and appearance groups still control Wedding-wide styling. Both title and kicker are bound after custom tab selection, and their callbacks capture the owning event state and content path. Shared Details/Timeline body editors, role data, tab names and page body layouts are unchanged.

`test/party-heading-ownership.test.js` covers cross-page/member/custom isolation, save/reload, reorder/role changes and retained legacy records. The shared appearance and server authorization suites check separate content keys/shared style groups and private guest projections. The maintained `scripts/verify-secure-state-browser.cjs` harness uses synthetic in-memory GitHub/R2 and the real local Worker: it edits headings with the actual editor, switches before flushing, tests custom/member pages with duplicate IDs, applies shared formatting, saves, reloads and verifies member views. It blocks external requests and does not contact production. It is an optional browser harness, not part of `npm test`; the Node regressions are in CI/deployment validation.
